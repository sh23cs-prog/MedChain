1. Introduction & Background

Modern electronic healthcare systems rely heavily on digital health records, yet sharing medical records across institutions remains fraught with peril:

🏥 The Medical Sharing Dilemma

Hospitals operate isolated databases. Transferring records requires unsecured email attachments, paper printouts, or manual faxing, creating massive clinical delays and diagnostic redundancy.

⚖️ Stringent Compliance Mandates

Regulations like HIPAA and GDPR require patient consent, strict access auditing, cryptographic confidentiality, and non-repudiation with severe financial penalties for breaches.

The MedChain Paradigm

A decentralized platform where patients own their encryption keys and define access policies, doctors access clinical records under attribute validation, and AI continuously monitors access behavior to preempt insider threats.

2. Problem Statement

Existing electronic healthcare systems suffer from four fundamental architectural flaws:

1. Centralized Single Point of Failure

Central hospital databases are prime targets for ransomware, administrative tampering, and catastrophic downtime.

2. Lack of Patient Ownership

Patients have no real-time transparency or control over which medical staff view or share their private health data.

3. Insider Threat Vulnerability

Compromised credentials or rogue staff can harvest thousands of patient histories without triggering static rule alarms.

4. Public Ledger Privacy Risks

Naive blockchain deployments expose real patient identities and wallet addresses, violating identity confidentiality.

3. Project Objectives

  • Patient-Centric Access Control: Implement fine-grained Ciphertext-Policy Attribute-Based Encryption (CP-ABE) allowing patients to specify criteria like (specialty=Cardiology AND hospital=CityHospital).
  • Authenticated Data Confidentiality: Guarantee off-chain storage security via AES-256-GCM authenticated encryption paired with SHA-256 integrity checks.
  • Identity Pseudonymization: Completely decouple patient identity from blockchain transactions using Keccak-256 pseudonyms (PIDs) and blinding nonces.
  • Immutable Non-Repudiable Auditing: Record every record upload, policy change, doctor authorization, and decryption event on an EVM smart contract ledger.
  • Real-Time Threat Detection: Deploy an AI microservice (Isolation Forest) evaluating 8 clinical telemetry features in under 15ms to detect anomalies.

7. Module Description

1. Authentication & Identity

Multi-factor registration with 6-digit BCrypt-hashed OTP via Resend & Brevo. Generates asymmetric keys and blinding nonce for Keccak-256 pseudonym (PID).

2. Patient Record Management

Client-side file selection, automated AES-256-GCM encryption, policy definition, and proxy re-encryption key delegation to authorized doctors.

3. Doctor Clinical Access

Query authorized medical records, request emergency access, and view decrypted records paired with real-time AI Risk Gauges.

4. Sentinel AI & Admin Oversight

FastAPI threat detection evaluating access telemetry in <15ms. Admin oversight dashboard with live system health and user management.

8. Security Architecture

  • Authenticated Encryption (AES-256-GCM): Encrypts files with 256-bit keys and 128-bit authentication tags, preventing ciphertext tampering.
  • SHA-256 Pre-Decryption Integrity Check: Every record computes a SHA-256 digest on plaintext; decrypted files are verified against the stored hash before rendering.
  • Cryptographic Pseudonymization: 
    PID = Keccak-256(Email || Nonce)
    Real patient identities never touch the blockchain.
  • Proxy Re-Encryption (PRE): The proxy transforms ciphertext from patient's public key to doctor's public key without ever decrypting or viewing plaintext.

9. AI Threat Detection (Sentinel AI)

Sentinel AI evaluates an 8-dimensional telemetry vector on every record access attempt:

8 Telemetry Features

  • hour_of_day (0-23)
  • day_of_week (0-6)
  • records_per_hour (velocity)
  • time_since_last (burst rate)
  • specialty_match (clinical alignment)
  • hospital_match (locality)
  • access_freq_7d (weekly load)
  • unique_patients_1h (harvesting indicator)

Model Performance (CICIDS2017)

Trained using Isolation Forest (150 trees, contamination=0.08):

  • Precision: 91.67%
  • Recall (Sensitivity): 99.00%
  • F1-Score: 95.19%
  • ROC-AUC: 99.84%
  • Inference Latency: 12.4ms

10. Implementation Workflows

Upload & Policy Workflow

  1. Patient selects medical record (PDF/PNG).
  2. Spring Boot generates AES-256 key & 96-bit IV.
  3. Payload encrypted; SHA-256 hash computed.
  4. Encrypted bytes saved in PostgreSQL & disk.
  5. Smart contract anchors hash on blockchain.

Access & Decryption Workflow

  1. Doctor requests record view.
  2. ABAC evaluates doctor's attributes vs policy.
  3. Sentinel AI evaluates access telemetry.
  4. If risk score < 0.75, AES payload decrypted.
  5. AccessLog recorded with blockchain tx hash.

13. Limitations & Future Scope

Current Limitations

  • Resend/Brevo free tier sandbox limits email recipients until domain DNS verification is complete.
  • Local Hardhat node runs in-memory; public testnets require faucet token management.

Future Enhancements

  • Zero-Knowledge Proofs (ZKP): Prove doctor qualification without exposing medical license details.
  • Self-Sovereign Identity (SSI): Integrate W3C Verifiable Credentials via MetaMask or Polygon ID.
  • Federated Learning: Train Sentinel AI across multiple hospitals without sharing access logs.
